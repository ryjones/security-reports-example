# gh cookbook — security-tracking

`gh` recipes for common tracker operations. Run from a clone of the tracker
repo, or pass `--repo example-org/security-tracking`. You RECOMMEND these
actions; a human runs the state-changing ones unless explicitly delegated.

**Read-only first.** List, view, and inspect freely. Any command that adds/
removes labels, comments, edits a body, or closes an issue changes shared state —
propose it, get the go-ahead, then run it.

## Find and inspect

```bash
# Untriaged queue (everything still awaiting/under triage)
gh issue list --label status:triage --state open

# One repo's open advisories
gh issue list --label repo:libparse --state open

# View an issue with its labels and full body (the body includes the snapshot)
gh issue view <N>
gh issue view <N> --json title,labels,state,body

# View comments (human triage discussion lives here and below the end marker)
gh issue view <N> --comments
```

## Label changes (human-owned)

```bash
# Advance status: a single axis — REMOVE the old status when adding the new one
gh issue edit <N> --remove-label status:triage --add-label status:confirmed

# Apply assessed severity (exactly one sev:*) and type(s)
gh issue edit <N> --add-label sev:medium --add-label type:memory-safety

# Mark a valid-but-not-security bug (disposition; do NOT use status:wontfix)
gh issue edit <N> --add-label not-a-security-issue

# Flag embargo
gh issue edit <N> --add-label embargoed
```

Only labels defined in `scripts/setup-labels.sh` exist. If `--add-label` errors
that the label is missing, you invented it — pick a real one or explain in prose.

## Comment (triage notes, verdicts)

```bash
# Post a triage report / note. It lands in comments — always below the
# snapshot region, so it is safe. Never paste embargoed content anywhere external.
gh issue comment <N> --body "Triage: symbols verified in libparse@<tag>; ..."
gh issue comment <N> --body-file /path/to/note.md   # for long write-ups
```

Anything an agent posts to GitHub MUST end with the attribution footer (see
SKILL.md → "Mark agent-written content"). Append it to the body/file:

```
---
🤖 _Generated by an AI agent ([Claude Code](https://claude.com/claude-code)) — a recommendation for VMT review, not a decision._
```

## Close with the correct reason

```bash
# Not a vulnerability / won't act / duplicate → "not planned"
gh issue close <N> --reason "not planned" --comment "Duplicate of #<M>."

# Fixed or published → "completed"
gh issue close <N> --reason completed --comment "Backports merged; closing."
```

Match the close reason to the policy in SKILL.md: `not planned` for wontfix /
duplicate / not-a-security-issue; `completed` for fixed / published. The sync
never closes issues — this is always a human step.

## Editing the body — caution

Prefer comments over body edits. If you must edit, edit **only** the human tail
below `<!-- /ghsa-sync -->`. Everything from the top of the body through that
marker is overwritten on the next hourly sync — edits there are lost and you
risk corrupting the machine region.

```bash
gh issue view <N> --json body -q .body   # inspect; find the /ghsa-sync marker
gh issue edit <N> --body-file /path/to/full-body.md   # must preserve the snapshot verbatim
```

## Manual advisory (non-GHSA reports only)

```bash
# Interactive, uses the "Security advisory (manual)" template
gh issue create --repo example-org/security-tracking
```

Do not file a manual issue for something that arrived as a GHSA — those mirror
automatically.
