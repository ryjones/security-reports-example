# Operating the tracker

Reference for mechanics of this repo. For deciding a verdict/severity, see the
triage skills; this skill covers only how state is recorded.

**Confidentiality:** this repo is private and embargo-sensitive. Never paste
issue/advisory contents, report text, or reporter identities into web searches
or any external service. Public-info lookups only. When linking a fix PR in a
public source repo, describe the fix neutrally — no vuln details while embargoed.

**Human/machine split:** you RECOMMEND labels, status changes, and closes for a
human to apply, unless the operator explicitly delegated the action. Never edit
the machine-owned snapshot region (see below).

`gh` command recipes live in **gh-cookbook.md** (same directory).

## Re-read state immediately before recommending

Operators apply labels, close issues and edit advisories themselves while asking
for analysis, so the tracker moves underneath a long session. **Re-query the
specific issues in the same turn as the recommendation.** A listing from earlier
in the conversation is not evidence of current state, however recent it feels.

This is the failure mode that a human cannot catch: a plan built on a stale read
is internally consistent, so it gets approved, and only the input was wrong.
Applies equally to GHSA state on the source repo, which operators also edit
directly.

## Duplicate reports: the earliest one survives

When one defect has several tracker issues, the **earliest-filed** issue stays
open and the later ones close as `status:duplicate` (not planned) — regardless of
which report is more detailed or which arrived with a patch. The surviving issue
is what establishes reporting priority for credit; a better-written later report
does not displace who found it first.

Compare **advisory creation dates** for mirrored GHSAs, not tracker issue dates —
the sync can create a mirror well after the report arrived.

Watch for one collision: a single report may describe two defects that belong to
different advisories. A GitHub sub-issue has only one parent, and closing children
when an advisory publishes would close such an issue while half of it is still
unfixed. Record the exception explicitly on the issue and in any coordination
issue rather than bending the rule.

## Writing tracker content people will actually read

Anything durable — coordination issues, triage notes, advisory prose — is read by
a VMT member opening it cold, weeks later, coordinating an embargoed response
under time pressure. Write for that reader, not for someone who followed the
analysis.

- **Do not invent shorthand.** Defect codes ("D1"–"D6") and names coined
  mid-analysis ("the parser patch", "the oldest-open rule") are unreadable outside
  the conversation that produced them. Name things descriptively or define them on
  first use.
- **No tracker jargon as prose.** Write "close #55 as a duplicate of #3", not
  "disposition #55 against #3".
- **Cut filler, not structure.** Sections that restate the standard response
  process, tables duplicating what GitHub's sub-issue tree already renders, and
  tables whose every row holds the same value are padding. The fix for a bloated
  document is better prose, not a terser bullet list.
- **Explain why**, not just what — why defects are grouped as they are, why an
  exception exists. That is the part a cold reader cannot reconstruct.

## Mark agent-written content — attribution footer

Any comment, issue body, or advisory text **you (an agent) post to GitHub
yourself** MUST end with this attribution footer, so a reader can tell an AI
drafted it and that it is awaiting human review:

```
---
🤖 _Generated by an AI agent ([Claude Code](https://claude.com/claude-code)) — a recommendation for VMT review, not a decision._
```

- **Applies to:** tracker comments (triage reports, notes), any manual-advisory
  body you create, and any other text you publish to GitHub directly.
- **Does NOT apply to:** a reply a human VMT member sends to a reporter under
  their own name (see **responding-to-reporters**). Once a human posts your
  draft as their own, they own it, and external replies stay free of
  internal-tooling detail — no footer there.

The footer is required whether or not the action was delegated: delegation
lets you post; it does not make the text human-authored.

## The two things people get wrong

1. **Status is a SINGLE axis** — one `status:*` at a time. `status:confirmed`
   means a confirmed *security* issue (the triage skills set the bar —
   confirmation needs evidence, not a plausible read); never put it on something
   you also call `not-a-security-issue`. A valid-but-not-security bug takes
   `not-a-security-issue` (a disposition, layers on top of status), NOT
   `status:wontfix` — it may still be fixed as an ordinary bug.
2. **Only labels in `setup-labels.sh` exist.** Never invent one
   (`repo:parse-playground`, `needs-repro`, `type:memory-safety (provisional)`
   are all illegal). If no legal label fits a nuance, write it in prose. The
   authoritative list is `scripts/setup-labels.sh`; the table below mirrors it —
   re-read the script if in doubt.

## Label taxonomy (owner + meaning)

| Label | Owner | Meaning |
|---|---|---|
| `advisory` | machine | Mirror of an upstream GHSA (managed by sync) |
| `withdrawn` | machine | Upstream advisory was withdrawn |
| `repo:libparse` / `repo:parse-server` | machine (on creation) | Affected source repo; must match `sources.yml` |
| `sev:critical` / `sev:high` / `sev:medium` / `sev:low` | human | Our assessed severity — exactly **one** per issue, never auto-applied |
| `status:triage` | sync sets on creation; human owns every later transition | Awaiting/under triage |
| `status:confirmed` | human | Confirmed valid **security** issue (evidence, not a plausible read — see the triage skills) |
| `status:fix-in-progress` | human | Fix being developed |
| `status:fix-ready` | human | Fix merged, pending release |
| `status:published` | human | Advisory published |
| `status:fixed` | human | Fixed/resolved and closed, **no advisory published** |
| `status:wontfix` | human | Will not act at all |
| `status:duplicate` | human | Duplicate of another advisory |
| `type:memory-safety` / `type:side-channel` / `type:logic-flaw` / `type:supply-chain` / `type:upstream` | human | Nature of the issue — may apply **several**. `type:logic-flaw` = authentication / validation / correctness flaw |
| `embargoed` | human | Under embargo; handle with care |
| `cve-requested` / `cve-assigned` | human | CVE lifecycle |
| `not-a-security-issue` | human | Valid report, determined not a security issue (may still be fixed as a normal bug); a **disposition** on top of any status |

Cardinality: exactly one `sev:*`; exactly one `status:*`; `type:*` may repeat.

## Legal status transitions

```
status:triage → status:confirmed → status:fix-in-progress → status:fix-ready → status:published
```
Terminal exits from triage/assessment (non-vulnerability): `status:wontfix`,
`status:duplicate`, or `not-a-security-issue`. `status:fixed` is the
fixed-and-closed-with-no-advisory path. `not-a-security-issue` is a disposition
that may accompany any status but must never sit with `status:confirmed`.

## Snapshot region — never hand-edit

`sync_advisories.py` owns a machine region of every mirror issue body. Exact
markers (quote from the script):

- **Start/meta:** `<!-- ghsa-sync-meta {"ghsa":...,"state":...,"updated_at":...} -->`
- **End:** `<!-- /ghsa-sync -->`

Everything from the top of the body through the end marker is overwritten on
each hourly sync. Everything **after** the end marker is human-owned and never
touched — put all triage notes there (or in issue comments).

The sync **never**: writes back to a source GHSA (one-way only); opens or closes
issues; changes any `sev:*` / `status:*` / `type:*` / `embargoed` / `cve-*`
label after creation (it sets only the initial `status:triage`); maps reported
severity onto a `sev:*` label (it shows it as "UNVERIFIED — assess
independently" text); or edits below the end marker. **Closing is always human.**

## Open-vs-closed policy (PROCESS.md)

Open/closed answers "is this still live?"; the status label records *why* it
ended.

- **Keep OPEN:** `status:triage`, `status:confirmed`, `status:fix-in-progress`,
  `status:fix-ready`. Also keep `status:published` open through backports/
  downstream follow-up, then close.
- **Close (terminal):** `status:wontfix`, `status:duplicate`,
  `not-a-security-issue`, `status:fixed`, and `status:published` once follow-up
  is done.
- **GitHub close reason:** `not planned` for wontfix / duplicate /
  not-a-security-issue; `completed` for fixed / published.

## Board fields (Project v2)

Sync writes only two objective fields: **Reported date** and **Source repo**.
Everything else is human-filled: Assessed severity, Status, CVSS, CVE ID, GHSA
ID, Affected/Fixed versions, Embargo/disclosure date, Assignee. The board's
built-in *Item closed → Status: Done* workflow handles the Done column. The
authoritative field definitions live in `scripts/setup-project.sh` — re-read it
if the field list here looks stale.

## Manual advisory issues

Use the "Security advisory (manual)" issue template **only** for reports that
did NOT arrive as a GHSA (e.g. a private email report to security@example.org).
GHSAs are mirrored automatically — never file one by hand. The template
auto-labels `advisory` + `status:triage`; do not set `sev:*` or `status:*` from
the reporter's claim.

See also: **triaging-security-reports** (the verdict process),
**responding-to-reporters** (reply drafts).
